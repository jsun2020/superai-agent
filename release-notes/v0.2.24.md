# SuperAI Agent v0.2.24

在使用 PAC 自动配置脚本的机器上，代理不再需要任何手动设置。

## 问题修复

- **配置了 PAC 脚本的机器仍然直连**：v0.2.23 让本应用读取系统代理后，Win11 机器依然收到拦截页。真正的原因由用户找到：这些机器设置的是 `AutoConfigURL`（自动配置脚本），而 **Windows 即使在 `ProxyEnable=0` 时也会遵循该脚本**。注册表里的这两个值互相独立，并非「开关 + 层级」的关系——因此一台注册表显示「不使用代理」的机器，实际上是完全走代理的。这也正是同一局域网内 Win10 正常而 Win11 失败的全部原因：Win10 镜像没有配置 PAC。v0.2.23 遇到 PAC 时只会打印 URL 并要求手动填写代理地址，而 PAC 是一段为每个 URL 计算代理的 JavaScript，本就无法用一个固定的代理地址表达。

  现在桌面端把该 URL 以 `SUPERAI_PAC_URL` 传给 sidecar，由 sidecar 抓取脚本并对当前服务商的地址执行 `FindProxyForURL`，据此设置代理。整个过程在启动时、构建任何 HTTP agent 之前完成，用户无需打开设置页。

- **v0.2.23 中的一处优先级错误**：`resolve_proxy_env` 先判断静态的 `ProxyServer`，PAC 只是其后的兜底分支。于是在同时配置了两者的机器上，本应用会走一个 Windows 自己并不使用的代理。现改为一个纯粹的 `choose_system_proxy`：PAC 优先，其次静态代理，最后直连，每个分支都有对应测试。

## 关于安全

PAC 是从网络上取回的 JavaScript，尽管指向它的是操作系统，它仍然是远程代码。脚本运行在 `node:vm` 沙箱中，其中只有 PAC 标准定义的辅助函数——没有 `process`、没有 `require`、没有 `fetch`——并设有 1 秒执行上限。URL 与主机名作为沙箱全局变量传入，而不是拼接进脚本源码，因此恶意主机名无法注入代码。这三点均有测试覆盖：给沙箱加入 `process` 会让隔离测试失败。

## 已知限制（明确取舍，而非默默出错）

- `dnsResolve` 在 PAC 规范中是同步的，而 JavaScript 中的 DNS 查询是异步的。因此目标主机会在进入沙箱前预先解析，查询其他主机则返回 `null`。常见的 `isInNet(dnsResolve(host), ...)` 写法可以正常工作。
- 脚本返回 SOCKS 代理时会跳过并尝试下一项（Bun 的 fetch 走 HTTP CONNECT，指向 SOCKS 端口只会让报错更难懂）。
- PAC 抓取限制为 8 秒、1MB。启动流程会等待该结果，因此一个失效的 WPAD 地址只会回落到直连，不会拖住应用启动。
- 设置页填写的代理、或环境变量中已有的代理，始终优先于 PAC 脚本。
- 失败绝不致命：任何一步出错都会保持环境原样并继续启动。

## 验证情况

在本机环回地址上搭建了真实的 PAC 服务与真实的、会记录日志的 CONNECT 代理，通过本应用自身的请求路径发起真实 HTTPS 请求，代理日志中出现 `open.feishu.cn:443`；对照组（不配置 PAC）日志为空，以确保该断言不会因为「什么都没发生」而通过。另有 43 项 bun 测试与 15 项 Rust 测试。

需要说明的是，测试用的 PAC 为自建脚本，**尚未针对真实的企业 PAC 验证过**。若升级后仍未生效，请提供 `AutoConfigURL` 指向的脚本内容以便排查。
