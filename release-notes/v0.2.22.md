# SuperAI Agent v0.2.22

修复便携版 Grep 工具完全不可用的问题，并把「企业网络拦截」错误说清楚。

## 问题修复

- **便携版的 Grep 工具一直不可用（ENOENT: uv_spawn 'B:\~BUN\root\vendor\ripgrep\...'）**：ripgrep 的三种解析模式在便携版里一种都走不通——只有显式设置 `USE_BUILTIN_RIPGREP` 为假值时才会查找系统 rg；内嵌模式要求 `Bun.embeddedFiles` 非空，而构建并未内嵌任何资源；于是回落到随包路径，该路径由 `import.meta.url` 推导，在 Bun 编译产物中是虚拟根目录 `B:\~BUN\root`，磁盘上不可能存在，而且构建也从未打包过 rg.exe。现在当随包二进制缺失时会回落到 PATH 查找（按裸名 `rg` 启动，沿用原有的防 PATH 劫持策略）；便携版本身已把 `vendor/` 目录前置到 PATH，因此日后放入 rg.exe 即可自动生效。已用「改回旧代码则失败、改回新代码则成功」的对照实验验证。此问题影响面不止于搜索本身：Grep 失败会迫使模型改用 shell grep 并多花好几轮对话，而每多一轮就多一次触发网络故障的机会。

- **「服务商返回空响应」的报错指错了对象**：v0.2.21 的诊断信息在出问题的企业 Windows 11 机器上直接定位到了根因——诊断打印出的响应体逐字符解码后是 `<html><head>\n<meta http-equiv=`，也就是说降级请求收到的是一张 **HTML 拦截页**，而非 API 响应；MiniMax 与 DeepSeek 表现完全一致，同时出现的 `InvalidHTTPResponse` 是 Bun 无法解析该设备返回的流式响应。这是网络设备拦截，不是服务商故障，但错误文案却写着「服务商返回空响应」，把排查方向引到了错误的地方。现在错误文案会依据实际返回内容选择措辞：返回 HTML 时明确提示「代理、防火墙或强制门户正在拦截对 <url> 的请求……这是网络配置问题，不是服务商故障」，并附上拦截页原文（拦截设备与策略名会自己出现在报错里，可直接拿给 IT）；返回其他非 JSON 内容时提示响应在传输途中被改写并附上内容；真正的空 JSON 响应措辞保持不变。已用模拟服务商的 `intercepted` 形态端到端复现验证。

## 新增

- `scripts/diagnose-provider-network.ps1`：在出问题的机器上运行，针对用户自己的服务商探测 {小请求, 大请求} x {流式, 非流式} 四种组合，输出状态码、耗时、content-type 与响应体摘要，一次运行即可判断网络设备到底卡在哪个维度。API 密钥从本地服务商配置读取，通过临时 curl 配置文件传递，不出现在命令行、也不会被打印，运行结束即删除。
